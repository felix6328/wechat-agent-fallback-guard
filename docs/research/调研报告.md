# AI 助手调用服务的出错兜底 Agent：二手用户调研

**性质：基于公开投诉与社区讨论的二手调研，不是用户访谈。** 调研时间：2026-11-17。共 71 条样本，原文链接见 `原始样本.csv`。

## 1. 方法与局限

- **来源：** 黑猫投诉、消费保、新闻媒体实测与报道（人民网、新华网、中新网、新京报、澎湃等）、微博、微信开放社区、GitHub issue（各类 Agent 框架与 MCP 工具），以及少量英文报道和帖子。
- **做法：** 手工检索，逐条阅读，不做批量抓取。打不开或需要登录的页面直接跳过，没有绕过：微信开放社区帖子大多要靠脚本渲染才能显示，小红书没有尝试。每条样本只记录一个具体事件或一句原话，引文都在 60 字以内。
- **获取方式：** 60 条是本人打开原页面读到的（45 条网页，15 条通过 GitHub API）。另外 11 条只读了搜索引擎抓取的正文摘录，没有单独打开原页面，CSV 里逐条标注了。
- **局限：**
  1. 媒体和投诉平台本身偏向报道严重案例，**所以计数只能看出痛点的种类和相对分布，不能算出发生率**。
  2. 有 9 篇报道各贡献了 2–3 条样本，同一篇报道里的样本不完全独立。
  3. 投诉都是当事人的单方说法。
  4. 样本只有 71 条，类别划分是我一个人做的，没有第二个人复核。

4. 豆包称退票只扣 5%，实际扣了 40%，损失 600 元；豆包承诺赔付，事后又说“我是 AI 没法转账”。[澎湃号](https://m.thepaper.cn/newsDetail_forward_33204502)，2026-05-21（A + C）
5. 外卖送错餐，AI 客服承诺“24 小时内全额退款”，人工客服称“AI 客服的回复不具有效应”。[开封日报](https://www.sina.cn/news/detail/5338742588178708.html)，2026-09-02（C）

7. 工具描述让模型每次都换新的幂等键。有人实测 48 次重试，其中 6 次造成重复退款。[square-mcp-server#31](https://github.com/square/square-mcp-server/issues/31)，2026-09/10（R）
8. 网友提问：“无法完成的任务它会拒绝执行并告诉用户原因吗？”[每日人物](https://news.qq.com/rain/a/20260917A08GJD00)，2026-09-17（F）

## 4. 洞察

1. **损失最大的时刻，是“说成了但没成”和“说失败但扣了钱”。** P 类 7 条全部涉及金钱损失。用户看到“支付失败”后，最自然的反应就是再付一次（样本 3、2）。微信支付官方的查单指引也写明：未收到结果时要先查单，并提示用户“不要重复发起支付”[文档](https://pay.weixin.qq.com/doc/v3/partner/4012082568)。这和本 Agent 的付款兜底设计一致，即“结果不明时只查单、不重试，提示请勿重复支付”。
2. **框架本身不可靠，“回复前核对”是必要的一层。** 13 条开发者侧 issue 涉及 OpenAI、Vercel、LangChain、NVIDIA、Claude Code 等常用框架，共同问题是工具失败被标成成功，模型据此宣布完成。另有 6 条 issue 显示，Agent 超时重试会造成重复扣款。所以不能假设上游会把错误如实传下来。
3. **最大的一类痛点，本 Agent 只覆盖了一部分。** A 类 22 条里，16 条来自通用助手（另 6 条是商家 AI 客服），从报道看多数**没有明确的工具调用，或只是基于网页搜索**，结果核对层没有结构化结果可查。另外，C 类“承诺不兑现”和 D 类“转人工难”合计 10 条，都发生在出错之后的补救环节，而本 Agent 目前只管到“转人工”这一步。

## 5. 痛点与 Agent 功能对应

| 类别 | 本 Agent 对应功能 | 覆盖程度 |
|---|---|---|
| B 假成功 | 操作后查询真实状态（查单、查订单），核对通过才回复“已完成” | 直接覆盖 |
| P / R 支付不明、重复扣款 | 只查单不重试，提示“请勿重复支付”，查不清转人工 | 直接覆盖 |
| X 工具失败被当成功 | 规则层不信任上游状态字段，按返回内容和业务规则重新判定 | 直接覆盖 |
| A 错误信息（有工具返回时） | 规则拦截明显错误，模型复核语义可疑的结果，必要时换数据源 | 部分覆盖 |
| A 错误信息（纯模型知识） | 无 | **未覆盖** |
| F 中断、无提示 | 失败时明确告诉用户原因和下一步 | 覆盖 |
| D 转人工难 | 有转人工，但不解决人工通道本身被堵的问题 | 部分覆盖 |
| C 承诺不兑现 | 无 | **未覆盖** |
| E 越权执行 | 无，本 Agent 在操作之后核对，不在操作之前把关 | **未覆盖** |

## 6. 建议的产品改动（2 项）

1. **关键事实必须有来源，否则降级表述。** 价格、退改规则、营业状态、订单状态这类会影响用户决策的信息，必须能在本轮工具返回里找到来源。找不到来源的，改成“未核实，请以官方页面为准”，并附上官方入口。这一项对应 A 类中没有调用工具的部分，NemoClaw#1452 讨论区也提出过同样的思路（回复里的链接必须出现在工具结果中）。
2. **承诺拦截加操作前确认。** 退款、赔偿、优惠券这类承诺，只有在工单或退款接口真实返回后才能说出口，否则改说“已提交人工核实，结果以人工回复为准”。取消、改价、付款等不可逆操作，执行前要让用户二次确认，并说明不可退的后果。这一项对应 C 类和 E 类，合计 9 条。转人工时把对话和订单号一起交给人工，避免用户重复描述（对应 D 类）。

## 7. 竞品公开信息速记（仅限本次找到的来源）

- **豆包：** 有两类相反的公开表现。
  - 负面：订票场景声称“已锁定席位”，实际并没有订单（齐鲁壹点实测）。豆包手机一代执行复杂购票任务时，几分钟后自动停止（新京报）。
  - 正面：豆包手机一代遇到高德受限时，会改用百度地图完成导航（新京报）。豆包手机二代在支付环节仍需人工确认（每日人物）。
- **千问：** 接入淘宝闪购后可以在对话内直接支付。实测中商品售罄后找不到切换店铺的入口，只能重新发起任务；推荐的链接还跳错了商品（AI 新榜）。
- **Kimi、文心一言：** 在订餐厅场景里明确表示无法直接预订，只给出步骤，选择不做而不是假装做成（齐鲁壹点）。
- **元宝：** 只找到事实性错误的吐槽，没有找到它在工具调用出错时如何处理的公开信息，**未知**。
- **OpenAI Operator（海外）：** 未经确认就下单买了鸡蛋。据《华盛顿邮报》报道，OpenAI 承认是安全防护失效，并表示会加强确认机制（来自搜索摘录）。
